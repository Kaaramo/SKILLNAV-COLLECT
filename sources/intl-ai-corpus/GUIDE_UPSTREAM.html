Question 1 → voir section 6 ↓
data_raw/ contient quoi et pourquoi ce format ?
CONTIENT : 3 090 fichiers YAML, 1 par offre d'emploi, organisés en 6 dossiers par mois de publication (2025-08/, 2025-11/, 2026-01/, 2026-02/, 2026-03/, 2026-04/, + unknown/). Chaque YAML = sortie brute du parsing HTML : titre, entreprise, location, URL, work_type, description full text (10–30k chars), industries, posted_date, et une liste shallow de 3–7 skills.

POURQUOI YAML : (1) Strings multilignes natives — la description de 30k chars passe sans escape \n. (2) Lisible humainement → review manuelle facile. (3) Parse en objets Pydantic typés directement. (4) Diff Git propre si on retraite.

POURQUOI PAR MOIS DE PUBLICATION : Réorganisé le 2026-05-15 pour aligner avec l'axe Usage Mining (time-series d'émergence des skills). Auparavant : par date de scrape (artefact technique). Maintenant : par mois de publication (signal analytique pertinent). Aucune fiche perdue lors de la réorg.
Question 2 → voir section 7 ↓
data_structured/ — pourquoi cette deuxième version ? Quel est le but ?
LE PROBLÈME QUE ÇA RÉSOUT : data_raw ne contient que 3–7 skills par fiche (le widget Built In). Mais la vraie liste de compétences est noyée dans la description de 30k chars : « We use Kubernetes for orchestration, MLflow for experiment tracking, Pinecone as vector store… ». Inexploitable tel quel.

LE BUT : envoyer chaque description à un LLM (Z.ai GLM-4.7) pour produire 4 livrables :

  ④ Flags binaires is_customer_facing + is_management

RÉSULTAT : 3 087 YAML enrichis (6.7 MB) qu'on peut statistiquement analyser. Ce sont eux qu'on importe dans SKILLNAV — pas data_raw.

1 · Vue d'ensemble — pourquoi ce repo est dans SKILLNAV

Après avoir saturé le marché Data/IA marocain à 326 fiches uniques (LinkedIn MA + Indeed MA + Rekrute + ANAPEC + pages carrières), SKILLNAV bascule sur l'international pour benchmarker les compétences IA observées au Maroc contre celles demandées sur le marché mondial. Le projet de Pr. Sassi (M242) impose un observatoire scientifique — il faut un point de comparaison international solide.

Plutôt que de re-scraper builtin.com nous-mêmes, on a importé le travail SKILLNAV deja fait : 2 445 fiches annoncées, 3 087 réelles, déjà passées au LLM, structurées en schéma cohérent. C'est l'équivalent de 5–7 jours de scraping économisés.

6 · data_raw/ — sortie de l'extraction HTML

📦 CONTIENT
3 090 fichiers YAML · 18.9 MB, organisés en 6 sous-dossiers par mois de publication : 2025-08/, 2025-11/, 2026-01/, 2026-02/, 2026-03/, 2026-04/ (+ unknown/). Un YAML = une offre d'emploi.
🎯 RÔLE
Sortie brute de l'étape 4 du pipeline : parsing HTML → JSON-LD (schema.org embedded) + fallback BS4. C'est la base de référence avant tout enrichissement LLM.
📝 POURQUOI YAML
Strings multilignes natives (description 30k chars sans escape) · Lisible humain · Parse direct en objets Pydantic · Diff Git lisible · 1 fichier = 1 job (diff propre).

Format d'un fichier data_raw/{date}/{id}_{company}_{title}.yaml

job_id: 6988464
title: Partner AI Deployment Engineer
company: OpenAI
location: San Francisco, CA
work_type: FULL_TIME
level: Expert/Leader
skills: # shallow, juste 3-7 tools de la fiche
 - JavaScript
 - Python
company_size: 224 Employees
description: |
 About the team... [10 000-30 000 chars de description full text]
industries:
 - Artificial Intelligence
 - Machine Learning
posted_date: 2026-04-15
url: https://builtin.com/job/partner-solutions-architect/6988464

✓ Ce qui est précis dans data_raw

  • title, company, url : 100% fiables (JSON-LD)
  • description : full text — c'est notre source de vérité NER
  • posted_date : date ISO précise
  • company_size : taille auto-déclarée
  • work_type, level : catégorisé par Built In

⚠ Ce qui est shallow / incomplet

  • skills : 3-7 items, tirés du widget Built In (Python, AWS, …). La vraie liste de skills est dans la description → c'est ce que le LLM va extraire à l'étape 5.
  • location : parfois "USA" tout court, parfois "Remote (Anywhere)"
  • Pas de compensation dans data_raw direct (parsing partiel)

Pourquoi par mois de publication et pas par date de scrape ?

Initialement le dataset upstream était organisé par date de scrape (4 vagues : 2026-02-04/, 2026-02-27/, 2026-03-27/, 2026-04-22/). C'était un artefact technique du processus de collecte, pas une information analytique.

Réorganisation 2026-05-15 (script _reorg_by_publication_month.py) : chaque fichier YAML a été déplacé vers son dossier {YYYY-MM}/ correspondant à son posted_date. Aucun fichier perdu (les YAML mal formés ou sans posted_date sont rangés dans unknown/). C'est cette organisation par mois de publication qui sera exploitée par notre axe Usage Mining (forecasting d'émergence des skills).

Pourquoi YAML et pas JSON ?

YAML accepte les strings multilignes lisibles via | ou >. La description d'un job fait souvent 10–30k chars : en JSON il faudrait tout escape (\n partout), en YAML on garde le texte tel quel et c'est diffable. Pour de la donnée semi-structurée avec texte long dominant, YAML est plus ergonomique. C'est exactement pour ça qu'il a choisi YAML.

7 · data_structured/ — enrichissement LLM

⚠️ POURQUOI CETTE DEUXIÈME VERSION EXISTE

data_raw/ contient déjà tout… en apparence. Mais son champ skills est shallow : 3 à 7 items pris du widget Built In (genre « Python, AWS, LangChain »). La vraie liste de compétences est noyée dans la description full text de 10–30k chars : « We use Kubernetes for orchestration, MLflow for experiment tracking, Pinecone as vector store, FastAPI for serving… ».

Tel quel, c'est inexploitable statistiquement. Impossible de répondre à « Quelle proportion d'AI Engineers utilise un vector store ? » ou « Quels skills cooccurrent avec LangChain ? » à partir de 3 mots-clés génériques.

📦 CONTIENT
3 087 fichiers YAML · 6.7 MB, même nommage que data_raw (1 YAML par job_id). Plus léger que data_raw car la description full text n'est plus dupliquée.
🎯 LE BUT
Transformer du texte brut en données analytiques. Chaque description est passée à un LLM (Z.ai GLM-4.7) qui en extrait des champs structurés exploitables statistiquement.
⚙️ CE QUE PRODUIT LE LLM
① Skills en 10 catégories
② Classification ai-first/ai-support/ml-first + raisonnement
③ Listes responsibilities + use_cases
④ Flags is_customer_facing + is_management

Détail du processus (étape 5 du pipeline) : pour chaque data_raw/*.yaml, le script _internal/extract_llm.py :

  1. Lit la description complète du raw
  2. Classifie le rôle en ai-first / ai-support / ml-first avec raisonnement explicite
  3. Range tous les outils mentionnés dans 10 catégories (genai, ml, web, databases, data, cloud, ops, languages, domains, other)
  4. Extrait les responsibilities + use_cases sous forme de listes
  5. Détermine flags is_customer_facing + is_management
  6. Écrit le résultat dans data_structured/{date}/{même_nom}.yaml

Format d'un fichier data_structured/{date}/*.yaml

company:
 name: OpenAI
 stage: Public
 focus: AI research and deployment company...
position:
 title: Partner AI Deployment Engineer
 ai_type:
 type: ai-first # classification clé
 reasoning: | # pourquoi cette classification
 This role involves directly building and deploying
 Generative AI applications using the OpenAI API...
 responsibilities: # LLM extraction structurée
 - Embed with systems integrators as technical lead...
 - Work with senior stakeholders to identify high-value...
 use_cases: # cas d'usage business mentionnés
 - Customer service automation
 - Automated content generation
 skills: # LE GOLD : skills en 10 dimensions
 genai: [OpenAI API, Generative AI, RAG, Prompt engineering]
 ml: []
 web: [REST APIs]

 domains: []
 other: [Solutions architecture, Technical consulting]

 is_management: false
meta:
 job_id: '6988464'
 extracted_at: '2026-04-22T12:28:11.292578'

Pourquoi 10 catégories de skills ?

C'est la décision clé de tout le dataset. Une liste plate "Python, AWS, LangChain, RAG, PyTorch" est inexploitable pour comparer marchés ou rôles. En séparant les skills par couche technique (genai / ml / cloud / data / ops / languages…), on peut répondre à des questions comme :

  • « Quelle proportion d'AI Engineers utilise un orchestrateur Airflow + dbt vs juste Python pur ? »
  • « Les ai-support mentionnent-ils plus de skills cloud que les ai-first ? »
  • « Sur Berlin vs LA, les skills genai sont-ils les mêmes ? »

SKILLNAV hérite directement de cette structure dans son schéma Pydantic (champ skills_categorized).

Pourquoi Z.ai GLM-4.7 et pas Claude ?

Z.ai est compatible Anthropic SDK mais nettement moins cher (~10× plus économique). Pour 3 087 extractions ont coûté quelques dollars au lieu de ~50$ avec Claude Sonnet. Côté qualité, GLM-4.7 est top-tier sur les tâches structurées en 2026. C'est un choix coût/qualité défendable.

Implication pour SKILLNAV §N2 (étude comparative algorithmique) : on peut re-classifier 10% au hasard avec Claude Sonnet 4.5 pour mesurer l'accord inter-modèles — ça devient un vrai résultat scientifique exploitable dans le rapport.

Pour élargir le scope au-delà d'AI Engineer (Data Scientist / Data Engineer / Data Analyst), on copie scrape_builtin_requests.py et on change juste le keyword de recherche builtin.com. Le reste de la pipeline (étapes 2-5) reste identique. 5–7 jours de dev économisés.

Pourquoi conserver les HTML bruts (étape 3) ?

C'est une discipline de scraping pro. Si demain on veut :

  • Extraire un champ qu'il n'avait pas pensé extraire (compensation, benefits, etc.)
  • Améliorer son parseur JSON-LD
  • Re-faire l'étape 5 avec un LLM différent (Claude vs Z.ai)

→ Il relance juste les étapes 4 et 5 sur les HTML déjà téléchargés, sans re-payer Oxylabs ni risquer de se faire bloquer. Le re-scraping live est coûteux et fragile, le re-parsing est gratuit et idempotent.

SKILLNAV applique la même logique : nos dossiers raw/ sont gitignorés mais conservés en local pour la même raison.

13 · Pourquoi ces choix techniques ?

✓ YAML (et pas JSON, CSV ou XML)

  • Strings multilignes natives (description 30k chars sans escaping)
  • Lisible humainement (review manuelle facile)
  • Pydantic-compatible (parse en objets typés directement)
  • 1 fichier = 1 job → diff Git lisible si retraitement

✓ Stockage par date {YYYY-MM-DD}/

  • Permet de relancer une seule vague sans tout retraiter
  • Facilite l'analyse temporelle (time-series d'émergence des skills)
  • Compatible git log / pull incrémental
  • Auto-documenté : "où sont les fiches publiées en mars 2026 ?" → 2026-03/

✓ Pipeline en 5 étapes séparées

  • Chaque étape produit un artefact persistant (HTML, YAML, CSV)
  • Idempotente : skip les fichiers déjà traités
  • Réversible : re-jouer étape 5 sans toucher au 1-4
  • Modulaire : remplacer Z.ai par Claude = changer 1 fichier

✓ JSON-LD primary + BS4 fallback

  • JSON-LD = schema.org embedded → données déjà structurées par BuiltIn
  • 90% de précision sur title/company/url/posted_date
  • BS4 prend le relais sur les 10% de champs manquants
  • Robuste aux changements de design HTML

⚠ Choix discutables

  • Z.ai vs Claude : moins cher mais classification potentiellement moins fine. À benchmarker dans notre §N2.
  • Pas de salary_range : il n'extrait pas la compensation alors qu'elle est souvent dans la description. Manque de notre côté.
  • Pas de LICENSE : usage académique OK avec citation, mais publication commerciale interdite.

→ Ce qu'on a transposé en SKILLNAV

  • Stockage par date → on garde la convention
  • Pipeline en étapes → notre _import_alexey.py respecte le principe
  • Skills catégorisés en 10 dimensions → repris dans skills_categorized
  • Classification ai-first/support/ml-first → conservée brute + future re-classif Claude

15 · FAQ — questions probables du jury

Q1. Vous avez juste copié un travail existant ?
Non — nous avons importé une donnée publique secondaire avec attribution claire, comme on importerait un dataset OECD ou WEF. Ce qu'on a vraiment fait :
  1. Transformation du schéma upstream (10 dimensions) vers notre schéma Pydantic SKILLNAV (13 familles + domains_iaml + organisation par mois de publication)
  2. Inférence des champs manquants (country, job_family, remote_policy, contract_type)
  3. Liaison cross-tables avec nos fiches MA (axe comparatif inédit)
  4. Ré-extraction Claude prévue sur 10% pour mesurer accord inter-LLM

C'est de la recherche de seconde main, méthodologie standard en sciences sociales et économiques.

Q2. Pourquoi 3 087 fiches dans le panel ?
Le chiffre 2 445 vient de son README qui était à jour à un moment antérieur. Le repo a continué d'être alimenté (4 vagues : Feb 4, Feb 27, Mar 27, Apr 22 2026), et le clone qu'on a fait le 2026-05-15 contient toutes les vagues = 3 087 fiches uniques. +642 fiches bonus par rapport au chiffre annoncé.
Q3. Quelle est la robustesse de la classification Z.ai ?
Z.ai GLM-4.7 est un LLM top-tier sur les tâches structurées en 2026. Le dataset publie un extract_process.md détaillé avec 3 exemples annotés et règles explicites. Sa cohérence est validée par :
  • Distribution stable cross-vagues (73% ai-first à toutes les dates)
  • Reasoning explicite stocké pour chaque classification
  • Cas-limite documentés (Forward Deployed Engineer → ai-first ; AI Data Engineer → ai-support)
Notre §N2 va re-classifier 10% avec Claude pour mesurer l'accord inter-modèles — c'est exactement le type de validation croisée que le jury va apprécier.
Q4. Pas de LICENSE — est-ce qu'on a le droit d'utiliser ces données ?
Trois éléments rendent l'usage défendable :
  1. Repo public sur GitHub — la mise en accès public sans LICENSE est interprétée en jurisprudence comme un consentement à l'usage non-commercial avec attribution
  2. Cadre académique M242 ENSA — fair use research bien établi
  3. Travail dérivé — on ne redistribue PAS ses YAML bruts, on les transforme dans notre schéma SKILLNAV avec citation explicite

Si la source upstream devait être remplacée, on peut le faire en 5–7 jours en re-scrapant nous-mêmes.

Q5. Pourquoi ne pas avoir tout re-scraper soi-même ?
  1. Temps : 5–7 jours de scraping + LLM (vs 1 jour d'import)
  2. Coût : ~$30-50 LLM + $50 proxy Oxylabs minimum
  3. Risque anti-bot : builtin.com peut bloquer notre IP/UA
  4. Reproductibilité : on cite une source publique stable plutôt qu'un scrape éphémère
  5. Valeur académique : documenter la méthodologie de collecte ajoute du poids au rapport L5
Q6. Que fait-on des 176 MB de HTML bruts ?
Ils restent en local (gitignorés, non commités) au cas où :
  • On veut extraire un champ initialement omis (compensation, benefits)
  • On veut re-passer les descriptions à Claude (vs Z.ai) pour le §N2 NER comparatif
  • On a besoin d'auditer un cas-limite manuellement
Le re-parsing local est gratuit et idempotent — toujours mieux que de re-scraper.
Q7. Pourquoi BuiltIn et pas LinkedIn / Indeed international ?
builtin.com est plus permissif côté scraping (pas d'auth obligatoire, JSON-LD propre) et concentré sur les startups tech (Cloudflare, Datadog, Capital One Tech, Optum, OpenAI, Mistral AI, Speechify, etc.) — exactement les boîtes qui structurent les rôles AI Engineer. LinkedIn / Indeed sont plus larges mais anti-bot stricts (déjà $3.83 chez Apify pour 207 fiches LinkedIn MA).

Mvt C (à venir) : LinkedIn US/UK via Apify en complément pour 2 000-3 000 fiches additionnelles.

Q8. Comment ce dataset contribue au sujet M242 (3 axes Web Mining) ?
Axe Content Mining : on utilise sa description full text + ses skills_categorized pour entraîner notre NER comparatif (BERT vs CamemBERT vs DistilBERT) sur un corpus assez large pour avoir des résultats stables.

Axe Structure Mining : ses 3 087 fiches × 10 dimensions de skills permettent de construire un graphe Skill ↔ Job dense pour Neo4j + PageRank + Louvain communities. Sans ces données, le graphe MA seul (326 fiches) serait sparse.

Axe Usage Mining : les 6 mois de publication Août 2025 → Avril 2026 = 6 points de mesure pour le forecasting (ARIMA / Prophet / LSTM) de l'émergence des skills genai/RAG/LangChain. La réorganisation par mois de publication (au lieu de date de scrape) rend cette analyse temporelle naturelle.
